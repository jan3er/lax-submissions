# lax-submissions

One directory per submission; each holds two Lake packages: `concepts/` (endorsement surface) and `proofs/` (requires `../concepts`).

Standing workflow from Jan (2026-08-06): **worker writes go into a cheap-seeded worktree per wave; the supervisor reviews the branch diff and lands it onto `main`.** Workers commit freely on their branch as checkpoints and never touch `main`. Parallelism follows the proof DAG, not policy: dependent leaves run sequentially; genuinely disjoint leaves (satellite files, different submissions) run in parallel at whatever width the supervisor judges reviewable on the fly — review bandwidth is the real constraint, not a fixed number. No planning/brief ceremony beyond the compact task packet unless Jan explicitly asks for it. Technical briefs are references, not mandatory process; when their seemingly required process sections conflict with this rule, this rule wins. `main` stays the supervisor's checkout: review, landing, campaign records, and the warm seed source. Preserve unrelated WIP, keep each edit narrowly owned, review the concrete result, and land each boundary before selecting the next dependent leaf.

The default supervisor rhythm is deliberately small:

1. Read the exact pinned source and the immediately relevant landed APIs.
2. Give one worker one coherent leaf in its own seeded worktree, narrow file ownership, and the semantic/build gates that actually determine correctness.
3. Let the worker run uninterrupted for about an hour. Do not poll, interrupt, or ask for status unless new information genuinely changes the task.
4. Review the concrete result for source semantics, preconditions, ownership, and cost claims. A checklist-complete but semantically weakened theorem is not complete.
5. Request only focused corrections, replay the narrow build, land the branch onto `main` (fast-forward or merge), remove the worktree, update the campaign record briefly, and commit that boundary before selecting the next leaf.

Inherited plans, retrospectives, and briefs are evidence about technical scope; they do not authorize extra workflow. Do not reread or restate the whole campaign when the next source leaf is already known. Do not create a plan document, worker brief, audit matrix, or parallel wave merely because an older document has a section for one. The proof is the work; process exists only when it removes a demonstrated risk.

Jan explicitly authorizes and requires staging, committing, and landing wave-owned work throughout this project — workers checkpoint on their branches, the supervisor lands onto `main` at every reviewed boundary. Do not stop to re-request permission at an ordinary completed boundary. Stage only the files belonging to that boundary and leave unrelated WIP alone.

Worktree mechanics: `git worktree add .claude/worktrees/<wave> -b worktree-<wave> main` (always name the base explicitly — tooling defaults can branch from a stale ref), then run `.claude/worktree-seed.sh` (no arguments) once before building or touching lean-lsp. The seed is a pure file copy from the main checkout — each package's `.lake/build`, `lake-manifest.json`, and `.lake/package-overrides.json`; the overrides resolve mathlib and friends to the machine-wide read-only warm store (`~/.lax/warm/`) in place, and the rev-pinned cross-submission requires to the sibling folders of the same checkout, so dependencies are never cloned or copied per checkout and no `.lake/packages` tree should exist in a submission. The seed reruns `.claude/sibling-overrides.sh` for the sibling half; run that script by hand after any `lax build`, which rewrites both generated files from the pins alone. Measured 2026-08-06: seed ~4 s, first `lake build` replays warm in ~3 min. If a package was never built in main, run `lax build --only proofs <submission>` once for it instead. Never run a bare cold `lake build` in an unseeded worktree. To land, review the branch diff from the main checkout, fast-forward or merge `main`, then remove the worktree promptly (disk is tight) and delete its branch.

- Build with `lake build` inside the package directory, `concepts/` before `proofs/`. Keep the build warm — the `lean-lsp` MCP tools time out against a cold build. In a fresh worktree run the seed script first (seconds instead of hours).
- On a machine with no `~/.elan` or `~/.lax` at all — a fresh Claude Code on the web container, or a new laptop — `.claude/dev-setup.sh` (no arguments, idempotent) builds that state from nothing, and is what `worktree-seed.sh` later copies *from*. It splits along the line the cloud environment cache draws. The machine half, `.claude/cloud-setup.sh`, installs the lax CLI, elan with the pinned toolchain, and the warm mathlib store — repo-independent, under `~/.elan` and `~/.lax`, ~4 min cold (warm store 177 s, toolchain 39 s), and it is the text to paste into the **Setup script** field of the cloud environment at claude.ai/code, because only that script's filesystem state is snapshotted and reused by later sessions. The checkout half — `lax pull-db` and every package's generated manifest/overrides pair — is cheap (~3 s) and per-checkout, so `.claude/hooks/session-start.sh` runs it at every session start; a SessionStart hook executes after the snapshot is taken, so nothing it writes is ever cached. dev-setup.sh calls both halves, so the hook alone still suffices on a container with no cached environment — it just pays the full four minutes there.
- Neither half touches the submissions' own `.lake/build`, but the archive already holds it: every `lax submit` that builds seals a capture of the compiled output — the `.olean`/`.ilean`/`.trace` companions and the `ir` C artifacts, per package — and pushes it to `ghcr.io/lax-archive/lax-captures` as a digest-addressed blob named by `capture.registryBlob` in the submission's `build-output.json`. `.claude/capture-seed.sh` (on demand, optional folder/id arguments) pulls those and installs them as `.lake/build`, which is exactly what lake reads to call a module up to date. Anonymous pull, digest-verified, and it never overwrites a package that already has a build. Measured 2026-08-08: 7 submissions (~407 MB) in 18 s, after which `ram-linear-time/proofs`, `sparsity-lectures/proofs` and three others each compiled **0** of their own modules. Where the tree has moved past the submitted commit the capture should still replay whatever did not change, exactly as a stale `worktree-seed.sh` copy does — expected from lake's trace model but not measured, so the script reports that drift per submission rather than promising a saving. `LAX_SEED_CAPTURES=all` runs it from dev-setup.sh; `LAX_SETUP_BUILD="<submission>"` compiles the working tree instead, for when no capture matches it.
- Toolchain is pinned in each package's `lean-toolchain`, mathlib by git rev in `lakefile.toml`. Never run `lake update`.
- Cross-submission dependencies are `(git, rev, subDir)` requires pinned to the dependency's current archive record (`~/.lax/lax-database/lax-N/record.json`, refreshed by `lax pull-db`) — a sibling `path` require is rejected by `lax build` and must never be reintroduced. Re-submitting a dependency moves its record, so every dependent's rev goes stale until it is repinned and resubmitted in turn; `.claude/sibling-overrides.sh` reports each mismatch it finds.
- Land at the end of every task (stage only the task's files; leave Jan's unrelated WIP unstaged).
- Campaign plans, night briefs, and other process records live in `plans/<submission-name>/` (index and old-name map in `plans/README.md`). Never leave them at the repo root; the root holds only `README.md`, `CLAUDE.md`, and `NIGHTLOG.md`.
- `plans/worker-brief-template.md` is conditional tooling for an unusually risky handoff. Default workers receive the compact task packet defined at the top of that file. “Required” sections are required only after the supervisor deliberately chooses the full template. The evidence trail behind the packet's clauses (and the corrections to it) is `plans/subagent-retro-2026-07.md`.
- The `lean-lsp` MCP server (`.mcp.json`) gives goal states (`lean_goal`), diagnostics, hover docs, `lean_multi_attempt`, and search (LeanSearch, Loogle, `lean_local_search`). Prefer these over rebuilding to inspect proof state. Remote search tools are rate-limited — batch queries. After changing imports or the toolchain, run `lean_build` to rebuild and restart the LSP; goal/diagnostic answers are stale until then.
